# Software factory requirements and pilot

**Decision brief · 20 November 2026 · proposed**

Build a factory that turns authorized work into **accepted, verifiable outcomes at a pace people can review**. Use existing work and delivery tools, a deterministic dispatcher for routine coordination, and agent sessions for work that benefits from judgment. Let developers start with their own approved tools. Add shared execution authority when work can be claimed or handed off automatically across machines. Start with meaningful review and recovery before scaling output.

## Requirements and assumptions

The following needs come from the brainstorming discussion. They describe the intended capability, rather than the scope of the first build.

| Requirement | What it means in practice |
| --- | --- |
| **Team-owned delivery** | Several developers can direct their own agents and contribute to the same project across machines and repositories. Architects can write code and developers can propose designs. Assign a human driver and approver for each consequential decision. People can inspect, steer, reassign, pause, and cancel work. |
| **Multiple ways to delegate and respond** | Support an explicit chat request, a Jira action, standing pickup rules, and configured events such as failed CI or PR reviews. A human can request a plan or PR change and get a revised candidate back. Preserve ownership while the execution role changes. |
| **Pluggable tools and agent choice** | Work can originate in Jira, Confluence, GitHub, or Bitbucket. Use existing artifacts, CI, and source control. Let developers choose among approved interactive tools and prefer a qualified runner for automation. Keep the work order, handoff, and review evidence portable across tools. |
| **Grounded work and verification** | Give workers the approved intent, code and contract versions, applicable conventions, and ways to prove behavior. Support design, planning, implementation, independent verification, debugging, and repair. Keep versioned team skills and access-scoped context across sessions and repos. Let developers keep private skills and preferences under the applicable project policy. |
| **Review capacity and accountability** | Limit review demand and give humans concise intent, test intent, evidence, and links to the consequential diff. Use deterministic checks and AI findings to help reviewers. Keep required human decisions effective. Offer risk-based auto-merge where the team's actual controls permit it. |
| **Operational diagnosis** | Connect CI failures, runtime signals, source, approved change intent, and resource inventory. Cover local, dev, staging, and production investigations at different access levels. |
| **Safe upkeep** | Find vulnerable or stale dependencies, plan and validate upgrades, verify what reached production, and use AI to improve the test harness. Keep automated rollout and mitigation tied to authorized release controls. |
| **Efficiency and learning** | Track model usage, cost, time, failures, and human rework. Choose cheaper models or lower effort when quality holds. Escalate difficult work. Let agents propose reusable skills and corrections to shared knowledge. |

**Inferred aims to validate.** A team should be able to adopt this without replacing its tracker or buying a new developer portal. The main constraint is likely reviewer attention and confidence in the evidence, even when code generation is fast. Independent sessions are useful for genuinely independent work and verification. Each additional role or model call should earn its cost. A small team may prefer a human-coordinated pilot before operating shared infrastructure.

**Open choices.** Pick the first repo and owner, which human controls apply, where the always-on process would run, which events are eligible for automation, what runtime data may reach a model, and how much review and compute capacity the team can commit. Treat the dispatcher as a component that could be adopted or built. The name does not imply a dependency on the Tasker project or test repository.

## Options and judgment

| Option | Where it fits | Failure boundary |
| --- | --- | --- |
| **Manual delegation with laptop agents** | First pilot. People choose work from Jira and start separate Codex chats or headless runs. Record handoffs in Jira, Git, and approved artifacts. | People coordinate overlapping work and offline handoff. Automatic takeover requires a stronger publishing boundary. |
| **Existing CI or hosted agent workflows** | Repo-local failed-build triage, scheduled scans, and dependency PRs. Reuse the existing runner and protected publication identity. | Check queue semantics, team access, provider support, and what survives a failed run. A repo-local queue is insufficient to coordinate a cross-repo change on its own. |
| **Deterministic dispatcher with laptop and optional hosted runners** | Multiple people or triggers can delegate to the same queue. Work must survive runner loss and resume through another eligible runner. | Requires a shared authority for execution claims or a backend that supplies it, plus an adapter that enforces it on external writes. Start with one writer per queue. |
| **AI coordinator for every task or peer-to-peer assignment** | Useful as an experiment for some discovery or planning tasks. | Adds reasoning, latency, and cost to routine routing. Shared chats and Jira fields still need a separate mechanism to grant exclusive execution rights. |

**Recommendation.** Run the first verified change with explicit delegation, then test an existing CI queue or Symphony-style scheduler before writing a service. Use one deterministic authority per queue once automatic pickup is enabled. If a shared ledger or CI already provides the required claim and publication semantics, reuse it. One host and a local database are sufficient to test the service alternative. Add multiple scheduler replicas only when availability or volume warrants it.

Keep **laptop ownership and orchestration authority separate**. Laptop runners can connect outbound, use per-attempt worktrees, and select a repo allowlist and concurrency limit. A hosted runner can accept approved team-queue work when people are offline. Use Desktop to learn the human interaction. Use `codex exec` for a first headless adapter with structured results and usage. Evaluate App Server when the workflow needs live steering, interruption, or approval interaction. [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode) · [Codex App Server](https://learn.chatgpt.com/docs/app-server) · [Symphony spec](https://github.com/openai/symphony/blob/main/SPEC.md)

A worktree isolates the checkout. Use a sandbox or separate runner identity when running untrusted code or handling sensitive context. Keep automated publication credentials in the trusted publisher, and keep untrusted candidate code out of that publisher's execution environment. Production data access and allowed model destinations are part of the runner policy. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use#mitigating-the-risks-of-untrusted-code-checkout)

### Division of authority

- **Jira or the chosen tracker** owns human accountability, priority, dependencies, and the visible work status. A project opt-in such as `Ready` plus `ai-ready` can express delegation. The Jira assignee stays the accountable human. Its assignment API documents setting the desired assignee without an expected-current-assignee precondition. [Jira assignment API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-assignee-put)
- **Confluence or Git documentation** owns the approved plan, architecture and business decisions, and durable runbooks. A change references the reviewed revision. **Git and CI** own candidate code, review events, checks, and build artifacts. **Deployment and inventory systems** own observations about what ran and where.
- **The dispatcher** owns attempts, leases, review capacity, budgets, and automated action receipts. It selects an eligible runner by project, repo, scope, availability, and user or team preference. An **AI coordinator** proposes decompositions, options, or repair plans when judgment is needed. It submits those proposals through the dispatcher.
- **Humans** own decisions under the project policy. Use DACI for consequential scope, design, and rollout decisions. The driver gets the decision made and the designated approver decides for the affected area. Contributors may code, plan, or review irrespective of job title. Eligibility and independence are checked separately.

Offer manual pickup, one-click delegation, and standing rules. All three resolve to the same work order. A rule might pick up a developer's ready test fixes while their laptop is online, capped at one task, ending at a draft PR. A CI event or PR review can create a work order directly. Link a Jira issue when prioritization, accountability, or cross-tool coordination calls for one. Support provider adapters for tracker, knowledge retrieval, runner, delivery and CI, runtime evidence, and execution storage. Each adapter declares what it can actually enforce. If a required gate is unavailable, stop unattended execution. A manual path is viable only where policy defines an equivalent control or an authorized exception.

### Handoff and recovery

Record a stable change and work-order ID, an attempt ID, pinned input revisions, runner and human identities, a lease generation, and a candidate reference. When the agent needs a human, record the decision required, the eligible person, the revision, and what can continue. Notify them in the relevant tool and release the compute slot. A mention gets attention. A verified decision advances work. An authorized request for PR changes starts a repair against the same PR within approved intent. Feedback that changes scope, contract, or risk goes to the responsible owner before implementation.

Treat a webhook as a wake-up signal. Deduplicate delivery, re-read authoritative state, and reconcile periodically. On takeover, a worker can keep local work, but automated publication must prove it owns the current attempt. The trusted publisher atomically reserves the external action against the current lease generation, allowed action, candidate revision, and effective policy before sending. A crash can leave a reservation whose remote outcome is uncertain. Keep conflicting writes blocked across takeover until reconciliation establishes what happened or an operator resolves the ambiguity. Reuse a stable logical action reference across attempts. Use provider idempotency or revision preconditions where available. An expired claim alone cannot cancel a remote write already in flight.

For cross-repo work, track one parent and a dependency graph of versioned candidates. Use compatible changes and explicit merge or rollout order. Record partial delivery as partial. Where a provider exposes a head-revision precondition, use it. Where it lacks an equivalent enforceable control, keep automated publication blocked. An asynchronous merge or queue acceptance still needs observed completion. [Jira webhook retries](https://developer.atlassian.com/cloud/jira/platform/webhooks/#retry-policy) · [GitHub merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously) · [Bitbucket merge queues](https://support.atlassian.com/bitbucket-cloud/docs/manage-pull-requests-with-merge-queues/)

## Agent choice, shared skills, and personal setup

Developers can implement from the same work order in an approved interactive tool. A colleague or verifier can pick up the candidate using its commit, the approved intent, an open decision or next step, and check evidence. For unattended work, a developer can select a preferred runner and explicitly allow fallbacks. The dispatcher checks that the team has qualified the runner for the repo, task, required capabilities, and data it will receive. If no permitted runner qualifies, the work waits with a clear reason. Authorize the destination as well as the data source when a runner sends code or context to a model.

| Scope | What to store and share |
| --- | --- |
| **Personal** | Keep editor settings, personal skills, shortcuts, and private notes with the developer. A developer can propose a reusable skill for team review. Personal setup applies to interactive work within project policy. |
| **Repository** | Keep build and test entry points, module conventions, local architecture references, and repo-specific skills in Git. Use a short shared `AGENTS.md` for orientation and a thin native entry point where a tool requires one. |
| **Team** | Keep reusable `SKILL.md` packages in reviewed Git history. A package can carry supporting files and tested scripts. Keep decisions, runbooks, and issue intent in their existing sources, with owners and links. Resolve only the relevant records the task identity can read, and record the revisions used. Reuse more sensitive context only in approved tools and environments. |

Use the Agent Skills format for shared authoring. Codex, Cursor, and Rovo Dev CLI document project discovery from `.agents/skills/`. Claude Code documents `.claude/skills/` and supports shared `AGENTS.md` under specific settings and versions. Keep one reviewed skill source and install or load the pinned copy through the qualified runner's native mechanism. Avoid relying on skill name alone. Discovery and precedence vary, and Rovo Dev CLI documents user skills winning over project skills of the same name. Qualify each launch mode separately. [Agent Skills specification](https://agentskills.io/specification) · [Codex skills](https://learn.chatgpt.com/docs/build-skills) · [Claude Code skills](https://code.claude.com/docs/en/skills) · [Claude Code instructions](https://code.claude.com/docs/en/memory) · [Cursor skills](https://cursor.com/docs/skills) · [Rovo Dev CLI skills](https://support.atlassian.com/rovo/docs/extend-rovo-dev-cli-with-agent-skills/)

For unattended runs, use a controlled runner profile, pinned shared skills, and approved tools and connectors. Read skill files and executable helpers from an approved revision. Require qualification to demonstrate that a same-name personal skill cannot shadow a required team skill, an unavailable required tool stops the run, and restricted context remains inaccessible. Record runner and skill versions and available usage data. Keep merge policy, credentials, and required checks enforced by the forge, CI, and trusted publisher. A skill can teach the agent to run a check. The check result comes from the trusted execution path.

## Review capacity, context, and compliance

**Expose one review-ready queue per team.** Limit both upstream candidate creation and items awaiting review. When capacity runs out, repair open changes, resolve blockers, or wait. Count drafts and abandoned attempts when measuring waste. Reserve an urgent path with an accountable owner. Approve shared intent once at the parent change where useful, then review focused candidates and their evidence. [DORA work-in-process limits](https://dora.dev/capabilities/wip-limits/) · [DORA small batches](https://dora.dev/capabilities/working-in-small-batches/)

**Make work reviewable before making it short.** Pin the intent, base commit, applicable contract, examples of local patterns, and preserved behavior. Specify acceptance examples and scope. Use permission-aware, task-scoped retrieval to supply relevant source and decisions. Surface missing or conflicting intent rather than silently resolving it. Keep the agent's temporary observations separate from accepted team knowledge. Save verified reusable lessons with an owner, source revision, and conditions for refresh. Publish generated or improved skills through review, test them on held-out cases, and record the skill version used in a run. [OpenAI harness engineering](https://openai.com/index/harness-engineering/) · [OpenAI skill evaluations](https://developers.openai.com/blog/eval-skills)

**Give reviewers one brief for the current candidate.** Include the decision requested, changed and preserved behavior, test intent, actual test results and missing evidence, risk, and links to critical diff locations. Show changed test expectations explicitly. Use static analysis, trusted CI, and a fresh reviewer to reduce noise before requesting human attention. Keep one current summary with actionable findings. Update the existing design or plan when it owns a durable decision. Include a diagram when a state transition, dependency, data flow, or topology changes. Generate it from schemas or manifests where possible and keep a reviewed design diagram with the code when the policy or rationale sits outside those sources.

An example brief might ask an owner to approve increasing an upstream timeout while preserving the total request deadline. Show that a delayed upstream response succeeds, a stalled response still respects the overall deadline, and a payment submission is sent once. Link the exact test run and the implementation paths that set deadlines and retry behavior. Show any unverified staging behavior in the same brief. A human can review the relevant design and implementation directly, with the full diff available.

| Proposed lane | Evidence and decision |
| --- | --- |
| **Allowlisted routine** | Require trusted checks and independent verification. Observe would-merge decisions first. Enable automatic merge for one qualified class only where controls allow. |
| **Behavior or contract change** | Human reviews the change's intent, test intent, evidence, and consequential parts of implementation. An eligible reviewer approves the exact revision where required. |
| **High impact or unclear** | Route financial controls, authorization, deployment and CI policy, irreversible migrations, uncertain evidence, and other protected changes to the relevant owners. An AI finding can raise the review requirement. A favorable AI assessment cannot lower a required gate. |

**Apply the organization's actual controls.** SOX Section 404 addresses internal control over financial reporting. SOC 2 change management criterion CC8.1 addresses how in-scope changes are authorized, tested, documented, approved, and implemented. The cited criteria do not prescribe universal human line-by-line review of every PR. Where the team's control requires independent human approval, preserve it and consult the control owner and auditor before changing the process. Treat a person directing an agent's implementation as a contributor when checking independence. Preserve the reviewed revision, actual check evidence, approval identities, build artifact, deployed version, and exception record. Protect the rules, tests, and credentials used to enforce the gate. [SEC Section 404 guide](https://www.sec.gov/info/smallbus/404guide.pdf) · [PCAOB AS 2201](https://pcaobus.org/oversight/standards/auditing-standards/details/AS2201) · [AICPA Trust Services Criteria](https://www.aicpa-cima.com/resources/download/2017-trust-services-criteria-with-revised-points-of-focus-2022) · [Craft change-control study](code-review-soc2-sox.md)

Capture approvals in the development tools where the applicable controls allow. Before automating a merge, verify that configured checks actually block it and that critical approvals are tied to the relevant revision. For example, Bitbucket distinguishes advisory checks from enforced checks. Reconcile observed deployments, including in-scope emergency or manual changes, against authorized artifacts. [DORA on change approval](https://dora.dev/capabilities/streamlining-change-approval/) · [GitHub branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [Bitbucket merge checks](https://support.atlassian.com/bitbucket-cloud/docs/suggest-or-require-checks-before-a-merge/)

## Operations, upgrades, and model routing

**Follow the deployed change.** Connect service, owner, environment, region, observed resource and config revisions, deployment ID, artifact digest, source commit and PR, and approved intent. Preserve observation timestamps and distinguish declared infrastructure from what was observed at incident time. Link the relevant trace, logs, and metrics. Start with a failed CI run and exact failing step. Expand to staging and then a redacted production snapshot. For ongoing production reads, give a tool backend scoped, temporary identity and enforce service, environment, time, redaction, and output limits. Keep production actions with the on-call owner and controlled release path. [OpenTelemetry log correlation](https://opentelemetry.io/docs/specs/otel/logs/#log-correlation) · [Backstage system model](https://backstage.io/docs/features/software-catalog/system-model/) · [Google SRE canarying](https://sre.google/workbook/canarying-releases/) · [NIST access model](https://csrc.nist.gov/pubs/sp/800/207/a/final)

Deduplicate repeated alerts and CI failures by source run or incident reference. Let a worker reproduce the failure in a controlled environment and return a draft repair or an escalation with conflicting evidence. Build repeatable evaluations using time-of-incident evidence, including unrelated signals and missing or stale data. Judge against a separately maintained diagnosis or expected uncertainty. For Bitbucket step logs, evaluate Atlassian's beta TWG CLI before building a new Craft transport. Check availability and access in the target tenant. [Datadog investigation evaluations](https://www.datadoghq.com/blog/engineering/bits-ai-eval-platform/) · [Atlassian TWG CLI beta catalog](https://developer.atlassian.com/cloud/twg-cli/commands/beta-commands-catalog/)

**Keep maintenance deterministic where practical.** Renovate or an existing updater proposes dependency changes. A scanner checks the dependency inventory and built artifact. Identify the affected deployments. Use an agent to read upgrade notes and actual call sites, adapt changed interfaces, investigate failed checks, and add targeted contract tests. A patch version alone cannot establish risk. Compare old and new behavior for intended compatibility. For higher impact, verify in staging and compare a canary against a baseline. Close the remediation when the intended artifact is observed where required. [Renovate automerge](https://docs.renovatebot.com/key-concepts/automerge/) · [OSV-Scanner](https://google.github.io/osv-scanner/) · [SLSA provenance](https://slsa.dev/spec/v1.2/provenance)

**Choose model and effort separately for each stage.** Start with a cheaper qualified profile for clear, bounded work. Use the stronger profile when a task requires deeper reasoning or difficult diagnosis. Escalate with exact evidence and a bounded retry budget. Keep issue resolution distinct from uncertainty that needs a human decision. Preserve essential context across profiles, retrieve large artifacts by reference, and measure tokens, metered or estimated cost, CI compute, human time, and all attempts per accepted change. Subscription usage without reliable dollar attribution stays a usage measure.

## Pilot and stop conditions

1. **Establish a baseline and complete one real change.** Use a representative repo and its existing human approval rules. Have a human request revisions on a plan or PR, then have an agent address the feedback and return a verified candidate. That first run establishes whether the workflow is usable. For evaluation, compare ordinary Codex work with comparable work that uses a pinned work order, fresh verifier, and short review brief. Track reviewer time, time to accepted change, rework, critical misses, scope drift, and cost across all attempts. Use separate comparisons if we need to isolate the effect of the brief or the verifier.
2. **Prove unattended coordination before expanding it.** Try one eligible queue and two runners. Race two claims. Kill or disconnect the winner, reassign, then bring the old runner back. Expire a lease after publication reservation and before remote completion. Drop a response after simulated remote acceptance. Push a new head after approval. Saturate the review queue. Require one active claim, rejection of a stale publish and stale approval, no conflicting write while publication is unresolved, and reduced intake when reviewer capacity is exhausted.
3. **Test the review and authority boundaries.** Feed a one-line high-impact change labeled routine, a candidate that weakens a required test, a bot's approval where a human is required, and a request missing trusted evidence. Confirm each waits at the appropriate gate. Run reviewer and model routing experiments on the same versioned inputs and judged cases. Evaluate auto-merge in shadow mode before enabling one narrow lane.
4. **Add one recurring workflow and one cross-repo change.** Replay a redacted failed CI run and prove diagnosis or clear escalation when evidence is inconclusive. Use one dependency upgrade or compatibility change across two repos. Deliberately fail the second step and verify the campaign reports partial state and preserves compatibility. A patched PR with an old artifact still running must remain open as a remediation. Add read-only staging and production evidence when the pilot exposes a specific useful source and its approved access boundary.

**Advance when the evidence shows less human time per accepted change at acceptable quality and control risk.** Agree on comparable case volume, representative negative cases, and acceptable thresholds with the owners before judging a pilot. Record queue age, abandoned efforts, and failed attempts alongside successes. Treat limited evidence about rare misses as uncertainty and keep the human gates if the data or controls cannot support a lighter lane.

The research supports the proposed experiments and boundaries. The team workflow, multi-runner recovery, authorization enforcement, and operating economics still require a pilot.
