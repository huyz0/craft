# Software factory delivery plan

**Delivery plan · Updated 23 November 2026**

The current delivery is the installable Factory, technical review and acceptance in disposable fixtures. A single operator can exercise separate owner, reviewer, verifier, runner and publisher identities. Use representative fixture work, simulated decisions and feedback, and explicit expected outcomes. Live tenant activation and organizational rollout are optional future work.

Start with one supervised Jira-to-PR repair. A simulated delivery owner delegates a bounded change, a worker implements it, and a separate verifier checks the exact commit. A simulated reviewer requests a change and the repaired commit returns to the same PR with fresh evidence. The initial workflow has one active review slot.

This plan implements the [MVP and end-state decision](../researches/factory-mvp-and-end-state.md) and [architecture and stack decision](../researches/factory-architecture-and-stack.md). The factory starts with a separate Rust executable and local SQLite. Craft provides bounded Jira and Confluence operations where qualified. The existing [Craft CLI OpenSpec ledger](../../cli/openspec/changes/build-cloud-cli/tasks.md) remains the authority for CLI implementation status.

The [launcher quickstart](../../factory/README.md) describes the implemented local workflow. In the earlier integration test, a synthetic Jira issue supplied the task and native Windows Codex produced the candidate. Bitbucket Pipelines ran the required step successfully on the initial draft revision and its repair. The launcher used a saved TWG OAuth profile to reject the earlier build as stale and record the repaired PR's exact source and base. Simulated feedback drove the repair. The source links are kept with the local rehearsal evidence.

The [handoff rehearsal](../../factory/pilot-handoff.md) was exercised from fresh extractions of both delivery ZIPs using a manual fixture repair. Its pre-repair bundle excluded the live repair commit. The updated verifier rejected a fixture that trimmed a non-string value and passed eight acceptance cases on the live repair and the corrected fixture. The [scorecard](../../factory/examples/pilot-scorecard.csv) records two completed Codex attempts and one repair cycle. Ordinary-work baseline, human minutes, and metered cost remain unobserved.

The kit includes an offline scorecard analyzer. It reports outcomes, attempt totals, measurement coverage, and metered cost by comparison path and task class. The rehearsal yields one simulated factory case and zero accepted changes. [Scorecard instructions](../../factory/README.md#try-the-supervised-workflow)

The [Windows packaging command](../../factory/tools/package-windows.ps1) generates the schemas from the selected launcher and runs the offline repair workflow from a fresh extraction before saving the kit. The Windows PR job additionally checks all bundled document links and exercises the Bitbucket and GitHub repair scenarios using the extracted executable. The GitHub scenario includes review handoff, change requests, replacement verification, approval evidence, and merge recording.

## What the delivery includes

The **MVP deliverable is an installable local workflow runner and verification kit**. The kit includes the launcher, a repo configuration example, work-order and receipt schemas, one pinned review skill, and a quickstart covering setup, delegation, review, repair, and recovery. A disposable CI fixture supplies trusted check evidence for local acceptance. Craft supplies provider operations where needed.

| Release | What people use | What runs on its own |
| --- | --- | --- |
| **MVP, through M3** | A developer starts a Jira issue from the launcher and can inspect, cancel, or explicitly resume the run. Developers can also work in an approved editor or agent and submit a commit through the launcher. Reviewers use the team's Bitbucket or GitHub PR page for the brief, checks, feedback, and approval. Jira carries issue ownership and intent, with Confluence available for a reviewed plan. | The launcher starts a bounded headless Codex process when requested. Existing CI runs the configured checks. The launcher keeps local state for recovery. Background polling and a standalone factory UI are deferred. |
| **First background workflow, M4** | The CI owner can select a failed run manually. After release approval, an opted-in failure can start the same workflow. The owner sees its result or escalation through the existing CI and review surfaces. | One CI job or trigger starts a bounded worker on eligible events. Publication follows the qualified path. This can ship using existing CI infrastructure. |
| **Shared team service, M5 onward** | Developers continue to work from tickets, PRs, their preferred agent, and the launcher. Operators use shared status and control commands to inspect attempts, pause intake, and recover. | An organizational service handles approved intake and dispatch. Connected laptop or hosted runners claim eligible work. A per-attempt agent is started on demand. A separate publisher performs authorized writes after qualification. |

A dedicated UI becomes useful when people regularly need to see work across repos and tools. Start with a small operator console for queue status, stalled work, pending human decisions, usage, and evidence links. Keep code review and approval in the forge. Prioritize the console after operators have used the shared queue and can show which questions the existing views leave unanswered.

The install kit includes a read-only terminal brief for operators. It combines queue health, waiting work, human decisions, forge holds, and recorded usage in one snapshot, with repository filtering and JSON output for other clients. It shows why each displayed waiting item cannot be dispatched and surfaces GitHub and Jira standing issues awaiting approval before they have a work ID. For first verification, it identifies which candidates have an active pickup, who holds it, and when it expires. [Operator brief](../../factory/shared/README.md#triage-the-shared-queue)

The supervised workflow also accepts a GitHub issue. Its adapter verifies the stable REST issue ID and canonical repository, pins the reviewed intent, and can recheck live state before worker start or draft binding. Migration 125 adds standing intake, and migration 126 requires an operator to approve the exact first input and any replacement. The shared fixture checks same-revision conflicts, reapproval, and the decision reference on the admitted work. ## Setup and automated verification

### Bootstrap the disposable rehearsal

1. Install the pinned launcher and Git. Copy the repo configuration into a disposable checkout. Pin the baseline, allowed paths, check policy and skill revision. Use fixture identities and temporary credentials. Native adapter checks can use installed executables with scripted loopback responses.
2. Run the setup check for tool versions, Git access, worktree and state permissions, sandbox availability and configuration. Report missing capabilities before starting an agent.
3. Run a bundled offline smoke scenario on a temporary Git repo and SQLite database. It delegates a sample issue, accepts a candidate, runs simulated checks, records a simulated request for changes, and verifies the replacement candidate. Ordinary development and CI use this mode without a Codex subscription, real tenant, or credentials. Demo identities and results are visibly marked as simulated.
4. Rehearse the supervised profile against the fixture repo. Use distinct identities for work, verification, approval and publication as required by policy. Check the exact revision, eligible reviewer, trusted issuer, allowed outputs and baseline. Verify the setup from a fresh extraction using the quickstart.

### Test at the boundary that can prove the behavior

| Layer | What is real and what is simulated | What the tests establish |
| --- | --- | --- |
| **State and policy** | Run production admission, scope, and transition logic. Inject a clock and use small in-process fakes for external inputs. | Invalid orders, duplicate delegation, budget and slot limits, cancellation, and stale evidence produce the right transitions. Advance the fake clock and use synchronization barriers for expiry and races. |
| **Storage and process** | Use actual temporary SQLite files and Git repos. Spawn a fixture executable in place of Codex. Test process supervision with controlled output, status, and termination. | The launcher survives restart, binds the actual Git commit, handles malformed or partial results, and cancels cleanly. Exercise Windows on the supported host because process-tree shutdown and file locks are native behaviors. Add actual PostgreSQL integration tests when M5 introduces it. |
| **Provider contracts** | Use small, versioned synthetic Jira, Confluence, and forge fixtures. Use loopback HTTP where wire behavior matters. Exercise the actual adapter parsing and request formation. | The adapter handles missing or stale fields, error classification, duplicate events, and the difference between a rejected write and a remote write whose reply was lost. Simulated responses are checked against documented contracts and qualified behavior. |
| **Executable workflow** | Drive the same CLI entry point used by developers through a temporary repo with Git, SQLite, a fixture runner, and fake forge/CI. Keep one end-to-end success path and targeted failure scenarios. | A candidate reaches review, a request for changes returns a replacement commit, stale approval cannot qualify that replacement, and a stopped launcher can resume. Check persisted state, user-visible output, and external action counts. |
| **Native execution and fixture quality** | Run pinned native adapters against scripted loopback responses and disposable repos with independently specified expected behavior. | Verify isolation, permission boundaries, tool behavior, exact candidate checks and reported usage. Keep real-model quality and billing outside the fixture result. |

Use a small risk-to-test matrix for mandatory invariants. A critical rule should have an explicit failure test that proves the gate rejects the wrong behavior. For example, run a candidate that weakens its own test, deliver an old approval for the replacement commit, and simulate a provider accepting a write before disconnecting. Test the decision in the fast suite and exercise the highest-risk failure again through the executable. Use line or branch coverage to find blind spots. Give priority to uncovered decisions about permissions, state, and external writes.

### Keep CI fast

| Gate | What runs | When |
| --- | --- | --- |
| **Required PR gate** | Formatting, lint, contract and fixture validation, and the full small deterministic factory suite. Include one executable smoke and critical recovery and approval cases. Use one required result that fails on missing expected jobs and records why a job was intentionally skipped. | Every factory code change. Documentation-only changes run link, task, configuration example, and contract-reference checks where relevant. Unknown impact or changes to shared contracts, policy, test selection, or the toolchain widen verification. |
| **Native and release gate** | Full deterministic suite plus install/unpack smoke, supported OS process and filesystem checks, and broader fault scenarios. | Native Windows smoke on launcher, process, or filesystem changes from the start. Broader platform matrix on main or a scheduled run, and on release candidates before publishing. |
| **Optional live qualification** | Verify provider permissions and checks, real-model quality and rollout behavior only for explicitly authorized future lanes. Keep live credentials in a protected job and keep untrusted candidate code out of that job. | Before activating a live lane. Requalify affected controls when the provider, profile, skill or production policy changes. |

- Start with ordinary Cargo tests. Keep expensive repository and executable setup in a small number of workflows and put most cases in fast, deterministic tests. Use temporary fixtures per case and reuse safe build artifacts. Keep sleeps, external retries, model calls, and tenant access out of the required PR path. [Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html)
- Cache dependency downloads and compatible compilation artifacts by OS, architecture, pinned toolchain, lockfile, and relevant build settings. Cache misses must still pass. Use the forge's standard cache and keep credentials, working databases, and raw agent data outside it. Avoid recompiling the same dependency graph in several parallel jobs when one build can feed the checks. [GitHub dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) · [Bitbucket dependency caching](https://support.atlassian.com/bitbucket-cloud/docs/cache-dependencies/)
- Keep test selection conservative. Run the full Factory suite for code changes and consider selecting individual code tests only if measurements justify it. Preserve the existing Craft CLI verification policy for changes that touch the CLI. Its verifier already has a local impact preview and a full qualification mode. [Craft CLI validation](../../cli/docs/validation.md)
- The Factory workflow limits its documentation shortcut to regular edits to an explicit list of guides and plans. It compares the merge checkout to the verified PR base and checks local Markdown links and linked JSON examples before reporting the required result. Changes to skills, configuration, tests, controls, or unrecognized paths run the full suite. Merge queues and manual runs also use the full suite. [Factory workflow](../../.github/workflows/factory-checks.yml)
- On the full lane, the Linux launcher tests and PostgreSQL integration run in one job. PR runs reuse the debug launcher built by the offline tests for the extracted-kit checks. Manual runs build the release launcher. Windows, Linux CI, and the local Linux qualifier run the same required CI repair and coordinator scenarios against the extracted launcher. `Factory required checks` waits for both platform jobs. [Factory workflow](../../.github/workflows/factory-checks.yml)
- Each platform job builds the launcher and queue into one Cargo target directory. Cargo can reuse dependencies built with matching features and compiler settings. The kit packaging steps use binaries from that directory, and the cache key includes both lockfiles, the toolchain, and the build profile. [Factory workflow](../../.github/workflows/factory-checks.yml)
- A manual release publishes one bundle after both platform jobs pass. The manifest binds both archives and receipts to the same source, workflow, run, and attempt. The installer verifies the bundle against the intended run and extracts the selected platform into a new directory. The release job exercises both installs before upload. [Verify and install a release kit](../../factory/README.md#verify-and-install)
- Record queue time, dependency setup, compile time, test time, cache hit rate, and flakes. Compare cold and warm runs separately. Use five minutes as a provisional warm-cache target for the PR job, then agree a p95 budget after measuring the runner used for qualification. When feedback slows, shorten the expensive step, consolidate duplicate builds, or move redundant coverage to a slower gate while retaining fast checks for mandatory rules.
- The optional **Report Factory timing** job adds each platform's runtime, Cargo cache result, and slowest measured steps to the run summary. The interval from the scope job's completion to a platform job's start is a dispatch delay. The workflow jobs API does not break out pure runner queue time. Compare the same lane and cache result over several runs before changing coverage. [Workflow jobs API](https://docs.github.com/en/rest/actions/workflow-jobs)
- Track factory behavior and agent effectiveness separately. Fixture results establish the workflow controls and comparison coverage under test. Optional future evaluations can measure real-model quality, human effort and cost on held-out tasks.

Replacing the approval returns the candidate to verification while preserving the audit history. [Shared dependency attestation](../../factory/README.md#verify-baseline-and-candidate-behavior)

Compatibility policies can pin an Ed25519 signing key for both CI receipts. The disposable fixture verifies signed passing and failing runs and rejects an unsigned substitution or a modified payload. [Signed CI receipts](../../factory/README.md#verify-baseline-and-candidate-behavior)

A single dependency work order can use the shared release series to track one exact deployment target. A passing compatibility verdict leaves it open. Closure requires an operator-approved rollout archive and the designated observer's verification of the reviewed change and running artifact. [Release series setup](../../factory/shared/README.md)

`prepare-rollout-archive` replays the pinned source manifests, checks all required targets and the reviewed head, and emits a catalog entry for operator review. The queue replays those inputs at its own observation cutoff before committing a receipt. [Rollout archive instructions](../../factory/README.md#verify-a-maintenance-rollout)

An operator can load a replacement rollout catalog by exact digest while the queue is running. The queue preserves its active catalog if the replacement fails validation. A newly loaded archive still needs its own ledger approval before it can close or refresh a rollout. [Reload the rollout catalog](../../factory/shared/README.md#verify-original-archives-on-the-queue)

## Optional live activation

If a live lane is needed later, nominate accountable people, approve credentials and data destinations, and verify the actual review, CI, publication and deployment controls for that lane. Use the pause, recovery and rollback procedures from the rehearsal. Measure human effort, real model quality and billed costs separately if those outcomes matter to the rollout decision. Production or tenant approval establishes authority only for the authorized lane.

## Independent review and vote

Three agents independently proposed milestone sequences, then reviewed the consolidated draft and voted on the same choices. The facilitator synthesized the decisions and did not vote. These are planning votes. The recorded votes describe the original rollout plan. The current milestones use fixture decisions. Real promotion decisions apply only if live activation is requested.

| Decision | Choices reviewed | Delivery reviewer | Controls reviewer | Adoption reviewer |
| --- | --- | --- | --- | --- |
| **What to build first** | **A** Manual walkthrough and thin local end-to-end workflow. **B** Runner and scheduler first. **C** CI repair first. | A | A | A |
| **What allows an expansion trial** | **D** Functional sign-off permits bounded learning if approved, with a separate comparison and promotion decision for regular automation. **E** Finish the comparison before any follow-on trial. **F** Functional sign-off alone permits regular automation. | D | D | D |
| **When to add shared authority** | **G** Selected CI failure first, followed by bounded same-authority intake. Shared claims require demonstrated need, and drafts have a separate gate. **H** Shared claims and publisher together before CI intake. **I** Native CI remains the sole authority for all team execution. | G | G | G |

**A, D, and G each won 3–0.** A manual walkthrough exposes approval and CI constraints before they are embedded in code. A narrowly scoped, human-selected CI trial can answer a new question without committing the team to regular automation. Shared claims address actual contention and takeover. Publication has separate consequences and needs its own tests and approval.

The alternatives remain useful under different conditions. CI-first is a better starting point if the owner narrows the initial objective to repeated repair in one repo. Wait for comparative results before any follow-on trial if it would consume scarce review capacity or change a protected control. Move shared claims forward if two unattended workers already need the same work. Native CI can remain the sole authority where it demonstrably satisfies the team's coordination and recovery requirements.
