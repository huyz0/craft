# Craft Factory Linux kit

Extract the archive into a new directory on a Linux host compatible with the distribution used to build the kit. From that directory, run the offline workflow with Git on PATH.

```bash
./craft-factory --version
./craft-factory --state factory.db doctor
./craft-factory smoke --destination "$PWD/offline-smoke"
```

Expect `passed: true` and `state: closed`. Use a fresh destination for each run. The smoke test uses synthetic data without an agent account or forge connection.

To check the packaged shared service before configuring your database, run the disposable smoke test as a non-root user. It requires Git, Python, OpenSSL, and the PostgreSQL programs `initdb`, `pg_ctl`, `createdb`, and `psql`. If the PostgreSQL programs are outside PATH, pass their directory with `--postgres-bin`.

```bash
python3 -B tools/smoke_shared_queue.py
```

Expect `passed: true`, `queue: paused`, and `candidate_handoff: independently verified`. The test installs the migrations in temporary PostgreSQL, starts the packaged queue on loopback HTTPS, and sends one Git candidate from a simulated worker to an independent verifier. It checks role isolation and deletes the database and credentials at the end.

For the shared queue, create a PostgreSQL database and service login. Set the PostgreSQL connection settings for the migration owner. With Python and `psql` on PATH, apply the included migrations. For the example below, `CRAFT_DATABASE_URL_FILE` points to a protected file containing the service login's database URL. Validate the server configuration before starting HTTPS.

```bash
python3 shared/migrate_queue.py --service-role craft_queue_api
CRAFT_DATABASE_URL_FILE=/path/to/protected/database-url ./shared/craft-factory-queue --check-config --bind 127.0.0.1:8443 \
  --certificate server.pem --private-key key.pem --identities identities.json
```

The [shared queue guide](shared/README.md#run-the-https-service) explains TLS, identities, and enrollment. Use the [workflow guide](README.md) for agent and reviewer handoffs, the [work order example](examples/work-order.json) for the first order, and the [verification skill](skills/verify-candidate/SKILL.md) for independent checks. The `schemas` directory contains the JSON Schemas generated by the packaged launcher.

After the queue starts and the runner passes preflight, use [shared work commands](shared/README.md#admit-and-manage-shared-work) to resume it and admit the approved order.

To keep the queue or Codex runner running after login or restart, use the [systemd installation guide](deploy/systemd/README.md).

To check one approved CI job on a schedule, follow the [CI repair timer guide](deploy/systemd/README.md#schedule-one-ci-repair-lane).
