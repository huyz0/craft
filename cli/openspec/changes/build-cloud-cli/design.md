# Craft Rust design

This is the implementation target, not an inventory of existing code. The workspace will live at `cli/`. The [proposal](proposal.md) owns scope, [capability specs](specs/agent-interface/spec.md) own observable behavior and [tasks](tasks.md) own delivery status. Earlier [provider architecture](../../../../docs/plans/cloud-cli-provider-architecture.md), [API catalog](../../../../docs/plans/cloud-cli-command-catalog.md), [auth plan](../../../../docs/plans/atlassian-agent-cli-plan.md), [agent interface](../../../../docs/plans/agent-cli-efficiency-and-skills.md) and [paging contract](../../../../docs/plans/list-paging-and-response-schema.md) provide detailed supporting semantics. This design supersedes their unrooted crate paths and milestone sequencing.

## Rust workspace and dependency direction

Reviewer configuration uses a separate per-profile/per-space `review_policies` SQLite table in private schema twelve, with format-one strict records bound to installation, grant, space, expected service actor, revision, enabled state, reviewer/exclusion lists and quorum. Missing rows establish no authority. Administration requires an explicit profile, apply, bounded complete receipts and exact revision; enabled records must be disabled before actor/target transfer. Eligibility changes are local access changes and invalidate captured policy. The separate `review policy get/set` family keeps reviewer fields out of ordinary provider-permission inputs. Native configuration performs no keyring or network access; public live review remains unavailable until complete inventory/source adapters are connected.

Review verification belongs in `craft-workflows::review` over a host-owned evidence port. Trusted policy construction is separate from deserializable approval statements; native host integration must load operator-managed reviewer configuration and verified current API observations, never caller evidence JSON. The verifier brackets complete root/reply inventories with live source/policy rechecks, bounds wall/monotonic age, binds plan/design revisions and resolved Jira mapping, counts distinct eligible reviewers and refuses unresolved/ambiguous decisions. Per-space policy excludes service/worker identities and declares human eligibility explicitly; account metadata alone cannot classify an account as human. The verified type has private fields and no deserializer. Future materialization revalidates it before each batch. Observations are bounded rechecks, not a cross-service atomic lock. Native reviewer administration and its checked bridge are now implemented; complete inventory adapters, public verification and durable workflow snapshots remain separate integration work.

Current page-bound footer comments use a distinct `confluence.comment.get` saved allowance and granular comment-read scope. The native request uses `/wiki/api/v2/footer-comments/{comment-id}` with current version included and no historical selector. Comment/page/container/status and version-author/time metadata are required. Optional raw storage/ADF content and a canonical fingerprint cover the exact body and version metadata. Existing page-read allowances do not expand; policy format and schema remain unchanged. These observations cannot establish original authorship, human eligibility, unresolved-request coverage or approval. Those require the later trusted reviewer and complete-review adapters.

Remote plan/design page-get adapters use the existing saved `confluence.page.get` policy and verified service read host. A fixed projection fetches current page identity, space, title, body and revision in the selected storage/ADF representation. The native page title overrides the duplicated standalone heading before semantic validation and digesting. The complete visible body is imported before output projection; document tenant/space must match the observed source. Responses carry page revision and semantic document digests as fingerprints, never approval. Parsing failures and output-budget errors retain bounded credential-cache receipts. No local file is read and no ticket/resource write is performed. Remote source snapshots are returned to the caller; durable workflow snapshots and approval rechecks remain later integration.

Typed `plan page-create` and `design page-create` adapters load and validate the complete local document, render its visible storage representation, and derive site/space/parent from document metadata before opening state or credentials. Plan publication requires proposed state. They delegate to the existing Confluence page-create host, saved policy and native journal; no Jira issue operation participates. The response uses the existing complete publication receipt, with the workflow command in the envelope and the native Confluence request/descriptor digests retained in journal bindings. These shorter workflow command names cannot enlarge the host's preflighted output. Publication is not review evidence. Page-get/update, exact-revision approval and ticket orchestration remain separate steps.

The first implementation task creates only the genuinely useful crate skeletons; no empty future-provider crate is required. `craft-core` imports no runtime/provider/workflow crate and performs no I/O. Runtime and providers depend on core ports; providers never own vaults or receive raw credentials. Workflows depend on core invocation/contracts, using provider-specific command types where needed, not a pretend universal task API. CLI composes the registry, runtime and selected compiled providers. Test-support may be a dev dependency, never a production/build dependency. Add Bitbucket/Trello modules only with working operation slices.

Use Rust with `clap`, `serde`, a JSON Schema implementation/generator, `reqwest` and explicit native keyring backends. Select and pin compatible versions, MSRV, TLS/CA behavior and native build prerequisites in bootstrap evidence. These are dependency choices to qualify, not installation claims. Prefer synchronous bounded command execution first; do not add an async runtime to every crate solely for future scale. Revisit only if actual cancellation/streaming/broker requirements justify it. A broker service may use async Rust independently.

Select SQLite for local operation/cursor state unless a measured platform/dependency constraint invalidates it. Use explicit schema migrations and transactional commits. It is not a credential store or a distributed authority. Store OAuth secrets only in native vaults. Protect local state/artifact directories with OS-appropriate ACLs; query/results can be sensitive even when not credentials. Do not use large hybrid-cache libraries for bounded continuation metadata.

## Operation model and extension contract

Core defines typed resource references, profiles/grants, request and result envelopes, effect classes, availability states, preconditions, operation outcomes and descriptors. A provider module returns an immutable manifest and registered operation handlers. A descriptor carries command ID, API/spec revision, schema references, selectable/default/required output fields, scope alternatives as OR-of-AND sets, product permissions, tenant conditions, native continuation/async behavior and retry/reconciliation class.

| Proposed Rust boundary | Responsibility and invariant |
| --- | --- |
| `ProviderModule` | Supplies identity/version, trusted deployment templates and registered operations; registration itself performs no network operation |
| `OperationDescriptor` | Owns request/response/field/effect/auth/recovery metadata; stable semantic command ID, separate from release and schema versions |
| `CanonicalRequest` | Contains validated typed inputs plus target and selection; canonical digest excludes secret material and nonsemantic diagnostic formatting |
| `PreparedOperation` | Holds exact effect, target, canonical digest and applicable preconditions; execution cannot silently substitute a newly interpreted payload |
| `OperationHandler` | Implements local validation/preparation, native result mapping and declared reconciliation; cannot retrieve raw vault tokens |
| `HttpTransport` | Applies trusted routing/auth, deadline/size limits, provider-aware retry and sanitized errors; request planning never exposes secrets |
| `CredentialStore` / `GrantSession` | Protect native secret generations and grant-scoped synchronization; distinguish service reacquisition from delegated rotation |
| `OperationJournal` | Commits intent and observed remote IDs/state; request acceptance and remote job completion are distinct records |
| `ContinuationStore` | Retains immutable traversal position, binding, provenance and unreturned records; never authorizes a target or silently skips data |
| `ArtifactStore` | Bounded safe file/stream access and atomic receipts under explicit roots; cannot execute downloaded content |
| `MutationAuthority` | Optional shared send/lease/fencing policy behind an actual enforcement boundary; absence selects explicitly weaker standalone consistency |

Choose concrete trait signatures and ownership/error/lifetime types in the owning task before code, keeping these boundaries. Use cancellation/deadline context consistently; do not leak a provider SDK type into core merely to avoid defining a stable wire/port type.

Core identities use explicit `ProviderRef`, `TenantRef` and opaque `GrantRef` values. They contain no credentials or configurable hosts. Resource references retain provider/deployment/tenant identity on the wire. Validation preserves raw values and refuses ambiguous whitespace/control characters; provider adapters add native identity constraints. `CanonicalRequest` validates its target, selection and preconditions before preparation. SHA-256 preconditions accept the versioned canonical digest form, not arbitrary text.

Patch input fields use `InputField<T>` with omitted, null and value states. A containing field uses a serde default and skips the omitted state on serialization; its generated schema is optional and nullable. Providers decide whether a given field permits clearing. Missing never silently becomes null. Operation receipts retain confirmed resources alongside request state and an optional independently typed remote job. Partial and uncertain failures can include those receipts in a failure envelope; they cannot be turned into success by the presence of confirmed effects.

An execution context exposes narrow host-owned ports: trusted HTTP requests, selected target identity, clock/deadline, artifact storage and operation journal. Provider handlers may construct only their declared method/path/body operation through the checked transport. They do not supply arbitrary auth hosts, raw token material, unrestricted redirects or a shell command. This is an extensibility contract and review boundary, not an isolation guarantee against malicious code linked into the binary.

The initial synchronous handler boundary uses `OperationHandler::validate` without a host context, followed by `execute` or declared `reconcile` with an `OperationContext`. `Registry::prepare` validates command input, target/deployment, output selection and local provider rules, then seals the request and descriptor digests in a private-field `PreparedOperation`. Registry execution refuses descriptor changes after preparation. A registered handler supplies a `NativeCall` with a declared route ID, raw path parameters, query and JSON body. The route descriptor owns method and literal/parameter segments; the host owns trusted origin selection, escaping, credential injection and response bounds. The checked context rejects unknown routes, extra/missing path parameters, undeclared query names and calls after cancellation/deadline failure before host invocation. Host responses cannot exceed the declared JSON budget. This does not implement HTTP, authorization, binary artifact transport or durable journaling; those remain separate runtime ports and acceptance work.

### Trusted JSON transport

Read adapters may declare repeated query parameters for native GET array filters. Add `NativeRoute.repeated_query_parameters` as an explicit subset of ordinary declared query names, disjoint from continuation names, and `NativeCall.repeated_query` as bounded vectors. Keep scalar calls unchanged; a name may not appear in both representations, and a declared repeated name must use the vector representation even for one item. Empty vectors, undeclared arrays, more than 100 values per name, more than 256 total query pairs, more than 32 distinct names or values above 16 KiB fail before connection. Preserve vector order and duplicate values; native adapters enforce semantic uniqueness/type constraints separately. Encode every value independently with the normal URL builder rather than joining or interpolating CSV/query text. Existing total URL bounds still apply.

Repeated declarations are qualified only for GET routes in this addition. POST JSON-array searches remain unchanged; mutation routes cannot acquire repeated-query support through this change. Empty repeated declarations are omitted from route serialization, preserving existing descriptor/digest behavior. Existing mutation claims remain unchanged because they reject GET routes and undeclared repeated values before journaling.

Next-link parsing accepts duplicates only for explicitly declared repeated names. Require an exact ordered match to the originally bound vector whenever a repeated parameter appears; omission retains the bound filter. Unknown names, scalar/continuation duplicates, added/changed/partial/reordered arrays, malformed encoding and cross-origin/path credentials/fragments remain refused. Rebuild requests at the original trusted endpoint. The special project-search site parser continues to require no repeated declarations. Test both pure declarations/calls and actual owned TLS wire encoding, connection refusal and continuation behavior before a provider uses the port. Jira field search is the immediate consumer; its native array filters must not be approximated by undocumented CSV encoding.

The runtime JSON context is constructed from a sealed prepared operation, its current registry descriptor, an explicitly selected grant and a host-owned tenant/grant-bound bearer session. Provider ports contain no raw URL, token, header or HTTP client. Initial Atlassian cloud origins are fixed at `https://api.atlassian.com/ex/jira/{cloud_id}/` and `/ex/confluence/{cloud_id}/`, with a validated cloud UUID. Route literals remain compiled descriptors; raw IDs are encoded once as individual path components, rejecting dot traversal, separators and already encoded identities. Query names must be declared and values are encoded as data. Context construction does not assert that a configured token has verified access; the auth/site layers must establish that separately.

An async reqwest client runs behind the synchronous core port on a private Tokio runtime. Redirects, implicit system proxies, automatic protocol retries, cookies, compression, referers, TLS key logging and verbose connection logs are disabled. HTTPS and certificate/hostname validation are mandatory. Platform certificate verification is the default; a bounded trusted launcher-supplied CA bundle may supplement it without a verification bypass. Requests use the remaining invocation budget and a cancellation-aware wait. JSON bodies are streamed to the route's byte bound and strictly parsed with duplicate/depth/container limits; invalid response content is never copied into diagnostics. Error responses expose status and bounded request/rate metadata rather than remote body text. Completed results take precedence over a late cancellation.

Native continuation normalization is a host port for GET routes. It accepts only the same origin and exact constructed route path, rejects credentials/fragments/duplicate or undeclared query names, and rebuilds a typed call instead of fetching an untrusted next URL. Wrong product/cloud IDs or changed path parameters cannot redirect credential attachment. Delta-seconds and HTTP-date rate advice are retained as typed metadata, without an implicit retry. Broker origins/flows, binary transport and operation-specific retry/job handling retain their separate acceptance. Production mutating contexts remain refused until durable send intent and recovery are wired; fixture-only mutation cases exercise conservative uncertainty without enabling a cloud write path.

Each route declares a unique subset of query names that continuation may change. Non-paging filters are retained and conflicting next-link values fail. Percent decoding is strict UTF-8, avoiding silent replacement of opaque cursor bytes. Registry registration rejects PUT/PATCH/DELETE on read descriptors while preserving POST-based search; endpoint semantics still require operation-specific qualification. The host context retains the prepared request digest and registry execution verifies that binding before calling a handler.

### Injectable clock and persistence ports

Core's `Clock` exposes wall milliseconds for persisted expiry and monotonic milliseconds for in-process deadlines; a wall-clock adjustment cannot extend an invocation. Vaults use a separate `CredentialStore` port with nonserializable redacted `SecretBytes`, zeroized on drop. Storage errors distinguish a known unchanged failure from an unknown commit outcome. No generic metadata/artifact store is a credential fallback. Providers never receive the vault port through their execution context.

`OperationJournal` creates immutable operation bindings (operation ID, request/descriptor digests, target and grant), then applies compare-and-swap record revisions. Per-step send markers must commit before a caller sends. A persisted `SendStarted` step is conservatively uncertain after a crash. Transition validation preserves confirmed resources/jobs and refuses binding changes, revision gaps and terminal regressions. It cannot establish actual remote effects or enforce a distributed lease. SQLite transactions, schema migrations, process locks and dispatch integration remain runtime work.

`ArtifactStore` begins a bounded writer under a validated logical artifact name. `finish` publishes a complete digest/size/provenance receipt atomically; dropping an unfinished writer publishes nothing. A commit can succeed while its acknowledgment is lost, so callers reconcile by receipt rather than overwriting or assuming absence. Competing writers cannot replace an existing committed name. These logical names are not OS paths: the native adapter must separately enforce trusted roots, safe open/create and junction/symlink/overwrite policy. Dev-only memory adapters implement these same ports with before/after-commit and write failpoints, explicit unavailable/locked vault states and restartable shared backing state. Their persistence is a simulation, never native durability evidence.

Compile the operation registry into command discovery, input validation and request/response schema views. Parser adapters for common flags must produce the same canonical request as file/stdin input. Complex payloads stay structured; do not invent a flag for every provider nesting level. Strictly close request objects, with metadata-validated extension maps for custom fields. Schema composition and response optional/null semantics need tests. Keep public wire models distinct from provider responses so provider changes do not silently change the CLI contract.

No arbitrary authenticated HTTP command ships by default. Start with compiled first-party clients. Later dynamic plugins require a separate versioned protocol, explicit install/trust, host-mediated capabilities and actual sandboxing if untrusted execution is promised. Repository files or fetched content never trigger plugin installation/execution. Do not extract a generic `WorkLedger`/`DocumentStore` until a second implementation demonstrates the shared semantics.

## Request and output path

The invocation control uses a monotonic deadline and an explicitly installed native Ctrl-C handler that only sets an atomic cancellation token. The initial execution budget is 60 seconds, configurable through `--timeout-ms` from 1 millisecond to one day. Normal file/stdin JSON reads run in a bounded worker while the main invocation polls cancellation/deadline; a blocked stdin cannot prevent structured termination. The CLI process releases a remaining blocked worker when it exits. This helper is not a general long-lived task executor. Checks before preparation/execution report pre-send cancellation; a host that has already sent must preserve confirmed/unknown effects and journal receipts instead of resetting state. Output publication preserves its completed envelope rather than replacing a confirmed result with a late cancellation.

Local operations accept an exclusive global `--input FILE` (or `-` for stdin) for their registered argument object. Explicit action flags cannot be combined with that source; default parser values are not merged into or allowed to override file input. Output controls such as fields and byte budget remain separate. The selected command path stays authoritative and JSON cannot choose another operation. Both sources undergo the same closed schema and typed conversion before dispatch. Missing required values fail schema validation even when the parser allows them to be supplied by JSON. Schema-query field selection supplied in both JSON and flags is a conflict, not an override.

The strict JSON visitor reports bounded JSON pointers for duplicate keys, syntax/type and size/depth/container failures, with a truncation indicator when a path cannot fit. It never echoes raw values or raw parser error text. Metadata-constrained field maps validate values against individually bundled field schemas from an exact resource-context binding; they cannot reuse a different tenant/project/type context or fetch remote schema references.

Typed registrations run the same strict Rust deserializer for `input validate`, JSON invocation and preparation, after ordinary JSON Schema validation. The schema's `x-craft-input-decoder: serde-strict` annotation declares this additional wire constraint and participates in its digest. In particular, a floating-point JSON representation such as `1.0` is not coerced into a Rust integer even though standard JSON Schema considers its mathematical value integral. Typed error reporting uses only escaped field/index paths, never the deserializer's raw value-bearing error message. Native metadata schemas remain individually bundled JSON Schema contracts; their exact target context is separate from this Rust decoder policy.

The path is parse → strict local schema/size checks → trusted profile/target resolution → capability/policy → applicable live preflight → canonical operation → execution/journal → projected bounded envelope. Local syntax/schema failure must precede HTTP/auth refresh. Local `input validate` and default `operation preview` make no network request. Explicit remote preview permits reads and ordinary auth maintenance only; `plan tickets-preview` is naturally a remote read workflow.

All ordinary commands are noninteractive. `auth login/provision --interactive` are explicit bootstrap exceptions. Errors preserve stable codes, field paths, write state and bounded recovery hints; raw provider bodies, tokens and full help dumps are excluded. Do not turn errors into executable suggestions from untrusted text. `--fields` selects response data, not mutation input; always preserve required control/identity/continuation evidence. Project upstream when supported, internally retaining native next/version/identity fields; otherwise bound and project locally.

Initial budgets remain 20 list items, 16 KiB envelopes, a 1–100 per-call item range, short discovery and a runtime skill body target of 600 tokens. The source contracts distinguish soft token targets from hard byte/parse budgets. Keep these values in one reviewed configuration/contract source and measure before calling them optimal. Refuse an output contract that cannot carry the minimum complete result. Large bodies, full scans and binaries use explicit artifacts with digest, path, media type and provenance. Never use an excerpt as a complete approved plan.

### Schema-backed field projection

Each descriptor declares a projection contract: a JSON pointer to the response item container relative to `data` (empty for a single object), mandatory fields, default fields and local/server/mixed execution mode. Selectable paths come from declared schema properties, not a separate permissive provider-field namespace. Arrays apply the same child selection to each element; numeric indexes and wildcards are rejected. Selecting a parent intentionally includes its declared subtree, while selecting a child includes no siblings. Duplicate paths are rejected rather than silently repaired.

Core compiles selected dot paths into a tree after validating every path against the response schema. The same tree projects values and the selected response schema. Local references and nullable object branches are supported; ambiguous unions or undeclared dynamic properties fail closed. A selected optional value can remain absent, and a real null stays null. Output projection does not assert why data is missing. Root envelope/error/control fields and data-container siblings stay intact. Runtime projection of provider reads will use adapter-declared server masks and preserve native continuation internally; local discovery can exercise the pure contract without claiming that transport integration is complete.

### Contract export and drift gate

The CLI composition crate exposes a development-only example exporter using the same Clap parser, typed argument adapters and operation registry as the executable. It enumerates leaf commands and compares their paths with registered operation IDs. Long flags must map to declared input properties or an implemented shared invocation control. JSON-only arguments and shared output controls are annotated on their source schema fields; newly skipped/unmapped arguments fail rather than becoming a second permissive input namespace. Parser examples and typed JSON decoding must produce identical argument objects. Export does not execute commands, open state or maintain auth.

`python tools/contracts.py check` compares deterministic generated contracts with `schemas/local-contracts.json`: full descriptors/request/response schemas, actual parser flags/defaults/choices, shared-control applicability, provider manifests, selectable paths and projection digests. `write` is an explicit reviewed development action. Missing scope/retry/reconciliation metadata, read-only retry on a mutation and parser/schema mismatches fail independently of snapshots. Empty scope alternatives explicitly mean no OAuth scope claim; they never prove a live credential's permissions. Future provider exports must use this same gate.

The checker reports bounded JSON paths and conservative compatibility warnings for removed/changed fields, flags and schemas. It does not claim a complete JSON Schema subsumption algorithm. Intentional public changes require inspecting the diff, requirements and version policy before regeneration. Negative controls mutate a flag, response property and selectable path, remove authority/recovery metadata and attempt invalid regeneration. The normal verification gate checks snapshots and executes those controls.

## Cursor and artifact state

Use short random local cursor handles over bounded protected state: immutable logical position, provider continuation, bound query/target/grant/schema/projection, fetched-but-unreturned records and expiry. Changing semantic query/target/fields invalidates continuation. Output size/item budgets may change without changing the provider-bound traversal. Return a specific expired/foreign/mismatched/corrupt cursor error; do not restart or invent an offset. Token refresh under the same identity/grant is not a semantic cursor change.

Fetch at most one native list page per ordinary invocation, without an automatic count. Empty/short pages may still continue. Persist any remainder before returning a usable cursor so byte/item limits cannot skip records. Do not move a shared mutable cursor on a read retry. Replay is not a snapshot guarantee for a live collection. Bound state size/retention and mark cached-fetch provenance. Permission visibility is the provider's at fetch time; the local cache is not a new authorization service.

### Provider continuation engine

Keep provider continuation separate from the existing typed local-profile cursor table. SQLite schema four adds `provider_cursors` with immutable random handles, payload byte bounds, expiry and an exact-payload digest. Migration from schemas one through three is atomic and preserves profiles, settings, grants, policy, journal and local-profile cursors. Refuse conflicting tables or triggers rather than repairing them. The digest detects accidental damage, not tampering by the same OS principal.

The core binding contains operation, descriptor/schema and projection digests, API revision, exact resource target, issued grant, verified actor and semantic query. Effective defaults must be resolved before constructing it. Output item/byte limits, local cursor and token generation are deliberately absent. Provider continuation is a bounded map of native parameter values, never a credential or routing authority. Each provider must validate its exact declared parameters and continuation semantics before making a fresh sealed request; the engine cannot validate a provider protocol on its behalf.

The runtime requires a host-owned source port to recheck access against that exact binding before serving either buffered records or a native page, and again before publishing output. This port is not itself a new proof of authorization. Provider adapters must compose it with normal verified actor/scope/permission access. The engine fetches only when the buffered remainder is empty and never fills the tail of a buffered page with another fetch. A successful empty nonterminal page returns a cursor and `native_page`; terminal pages return `exhausted`. `item_limit` and `byte_limit` mark locally retained remainder as truncated. Observation time and normalized native-page digest survive buffered replay, with an explicit cached flag. All traversals are labelled live.

Persist the full first unreturned item and native continuation before exposing a successor handle. If the first item cannot fit, return an `ITEM_TOO_LARGE` result with zero items and a recovery cursor at the same position; first preflight the complete bounded recovery envelope before fetching. If even that envelope cannot fit, refuse with `OUTPUT_BUDGET_TOO_SMALL`. Never skip an item or return a handle whose state did not commit. A callback failure, cancellation or persistence failure returns no successful page. Original handles remain replayable, including after concurrent replay or failed successor publication. Replaying a handle that needs a live fetch may observe changed provider data and is not a snapshot.

Use a fixed fifteen-minute traversal lifetime, at most 256 unexpired handles, one MiB per stored payload and sixteen MiB aggregate stored payload. The adjustable output limit remains one through 100, matching the shared selection contract. Normalize at most 1,000 records and 512 KiB per native page; a larger provider page fails explicitly without emitting a partial traversal. Retain at most 256 digests of requested native positions, rejecting repeated/cyclic continuations as `PAGINATION_STALLED`. Capacity/expiry failures require explicit recovery or a new traversal, never hidden eviction of live handles or silent restart. Validate stored payload shape, exact digest, installation, binding, timestamp order, continuation/history and bounds on every load. No credential material belongs in a cursor.

The first engine slice deferred Jira project discovery. The official [pagination guide](https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/#pagination), inspected 10 November 2026, confirms that `maxResults` is a maximum, totals can change and pages can be empty. It does not establish a short-page arithmetic advancement rule. The project adapter below uses the explicit `nextPage` contract and a narrow site-link parser. No generic next-link trust relaxation is selected.

### Contextual current-user permission reads

Implement the GET `jira.permission.check` view through `/rest/api/3/mypermissions`, using an exact site/grant/actor policy and verified service access. Require one to 32 unique explicit permission keys, preserving order. Accept bounded ASCII alphanumeric/dot/underscore/colon/hyphen plugin keys, excluding CSV separators and whitespace. Construct the documented native CSV only from those validated keys; do not expose another-user, arbitrary query, configuration-UUID or bulk-POST controls in this view. Use the pinned current classic `read:jira-work` scope; the pinned beta granular alternative is not activated by the live guide alone. Bulk/other-user variants remain separately qualified follow-up.

Allow zero or one explicit project ID/key, issue ID/key or numeric comment ID. No selector means global context. Validate selectors locally and send only the corresponding native query parameter. Preserve the exact requested selector without claiming resolved identity or resource existence: the native response does not echo either. Expose static context kind and project-permission evaluation semantics: any project globally, any qualifying issue/project for a project, requested issue/containing project for an issue, and comment visibility plus parent-issue permission for a comment. Comment context accepts only BROWSE_PROJECTS. Global permission kinds are unaffected by these contexts. A reported true is not proof of an operation's workflow, screen, issue security, app-access-rule or value constraints, nor mutation authority.

Emit one result per requested key in request order. Missing native entries have `returned:false` and `have_permission:null`; missing decision flags remain null, never false or true. Require boolean decision flags when present, exact native key/map-key agreement, bounded inert optional labels/type/IDs and no unexpected permission entries. Always preserve key, returned state, decision and missing-field indicators under projection. Unknown properties are inert and omitted; warnings/errors, malformed native types, duplicates and bounds failures release no partial page. Preserve global/project permission kind when returned so callers can interpret context. A private in-process observation binds operation/principal and 60-second dual-clock freshness, rejects backward clocks and cannot be reconstructed from cached/serialized data or authorize a write.

Buffer the bounded unpaginated result through the existing immutable list host. An active busy/locked commit can retry only `COMMIT`, never its transaction body; cancellation/deadline rolls back uncommitted state. Other commit errors retain uncertainty. An application ID and schema version distinguish Craft state from foreign databases; unsupported/corrupt state is refused rather than repaired. The fixed-page database is capped at 64 MiB and stores at most 1,000 profiles. Schema two adds bounded local mutation records through the explicit migration below. Installing native-backend metadata does not claim the backend adapter is available.

`profile.list` reads at most 101 ordered summaries per native fetch, with default output 20 and maximum 100. Immutable random cursor handles bind the installation, descriptor and effective projection. Cached remainders retain their observation time and expire after 15 minutes; at most 256 unexpired cursors are retained, with explicit capacity failure. Budgets may change while resuming. Cached observations are marked; traversal remains live rather than claiming a cross-page snapshot. Missing, foreign, mismatched, expired or corrupt handles fail without restarting. This initial adapter qualifies local profile traversal only, not provider or generic operation-journal persistence.

Private root operations live in a leaf `craft-platform` crate. Other crates retain unsafe-forbidden linting. The platform crate denies unsafe by default and permits only necessary private native FFI wrappers, with explicit allocation/handle lifetime contracts and native tests before CLI enablement. Existing root/database ownership and ACLs must pass verification; the CLI never repairs a foreign/insecure directory implicitly. Unix uses owner-only modes, no-follow opens and trusted ancestor ownership/write checks. This is not isolation against malicious code running as the same OS principal. See the native safety record for reviewed calls and remaining OS qualification.

A profile names provider/deployment/tenant/default targets and references an opaque grant ID. Trusted user configuration owns auth hosts, broker, credential backend and reviewer policy. Repository hints may select authorized targets/content but cannot redefine trust. ### Service token exchange

The internal service client sends one form-encoded POST to compiled `https://auth.atlassian.com/oauth/token`, containing only `grant_type=client_credentials`, `client_id` and `client_secret`. It reuses the host TLS policy without redirects, proxies, cookies, compression, TLS key logging or automatic retries. No runtime/provider URL overrides, alternate grant types, audience guessing or implicit delegated refresh are accepted. Secure provisioning input is consumed as a bounded zeroizing JSON buffer; unknown/duplicate input fields and malformed secret text fail locally without echoing values.

Successful responses are bounded to 64 KiB and parsed directly into zeroizing secret fields, avoiding a generic JSON value containing the access token. Duplicate top-level parameters, invalid bearer encoding, invalid scope grammar, absent/invalid expiry and unsafe lifetimes fail. OAuth extension values are ignored within bounded input/depth; a refresh-token extension never selects delegated behavior. An omitted scope remains unknown. The token lifetime is calculated conservatively from request start using both wall and monotonic time, with an early reacquisition margin. Returned expiry is used rather than assuming a fixed hour; the local maximum accepted lifetime is one day. Client IDs are bounded to 1 KiB, client secrets to 64 KiB and bearer tokens to 16 KiB, without assuming a fixed credential length.

The client returns redacted opaque token ownership and non-secret expiry/scope metadata. No secret getter/serialization is exposed. Auth failures omit bodies and free-text headers while retaining typed rate advice; uncertain/cancelled exchanges preserve possible token issuance without claiming a product-resource mutation. Current-user reads use compiled Jira/Confluence routes and require reported probe scopes. A session requires a successful proof for its exact provider/Cloud ID; all proofs bind the first observed actor. Failed revalidation removes that target's proof while retaining the actor binding, and read failures do not claim possible product mutations or token issuance. Keyring activation, explicit organization eligibility and operation-specific scope/resource-permission checks remain separate gates. Client credentials are reacquired, never rotated through the delegated refresh algorithm. These internal interfaces do not enable an auth CLI command or claim a live eligible tenant.

Rotation takes a cross-process grant lock, rereads committed state, exchanges once, persists/verifies the new generation before activation, then cleans obsolete state. Invalid grants require explicit reauthorization. Lost rotation responses and failed persistence have documented recovery rather than a retry storm. Local logout must not resurrect credentials via a racing refresh. Report local removal separately from provider revocation; implement remote revoke only against documented/tested endpoints. Status/doctor reveal metadata and store health, never token bytes.

### Service grant cache

Secure pipe input has a separate secret-aware worker rather than using ordinary argument JSON. The production entry point checks the native stdin source is a pipe before reading; terminals, redirected regular files and argv values are not secret fallbacks. Explicit interactive input owns one process-local terminal guard on the calling thread, disables echo and line processing and polls bounded native events while the runtime checks cancellation/deadline. UTF-16 events and Unicode-aware deletion are supported on Windows; the Unix adapter uses nonblocking raw UTF-8 input with saved termios/file flags. The guard restores prior state on success and handled failure, with a checked finish and a best-effort drop fallback. Restoration failure prevents credential use and reports terminal-reset guidance. Forced termination or an external competing terminal reader is outside the guard guarantee. This API requires exclusive foreground terminal ownership and is not used by ordinary agent commands. Actual native acceptance is required separately on each platform.

Local `auth status` resolves trusted profile context, obtains its grant lock and inspects only the bounded generation index. It reports absent, stored-unverified or recovery-required state, cleanup pending, unknown token validity and the profiles sharing the grant. Neither command exchanges tokens, initiates login, performs product requests, repairs storage or writes native credential items. These local diagnostic commands do not enable the consequential provisioning/refresh/logout or cloud path, which still requires its independent review and eligibility gates.

A service grant persists one strict, versioned secret bundle in the existing native generation store: grant identity, configured product/cloud targets, actor binding, provisioning credentials and cached token/expiry/scopes. Explicit provisioning verifies all configured targets before replacing a generation. Reuse cannot add targets or switch actors; changing that authority requires explicit reprovisioning. Missing, corrupt or unresolved generations fail before OAuth acquisition; logout's inactive state never triggers implicit login.

Provisioning offers a host preflight after product proof and before keyring replacement. It exposes only safe token metadata and verified identities, allowing the CLI to freeze complete projected activation/recovery envelopes before commit. Local activation failures carry a separate optional credential-write state; token-issuance uncertainty alone never implies a keyring write. Token scope text is checked for reflected client credentials or bearer bytes while still in zeroizing response storage, before allocating public scope metadata.

The provisioning composition candidate accepts explicit bounded profile aliases, an expected service-account actor and exactly one secret input source. All selected profiles must use service auth and share an issued grant/authority; product/cloud targets are validated and deduplicated from trusted profile metadata. A configured browser administrator identity is never substituted for the service actor. Existing active credentials require explicit replacement, and unresolved staging is refused before secret input. Eligibility is established by actual issuer acceptance plus scoped current-user proof, not by an agent-supplied `eligible` flag; no usable grant is activated on an unsuccessful qualification attempt. This does not assert project/space write permission.

The candidate is not registered in the public parser/catalog before consequential review. It returns a complete envelope, freezes success and recovery data before activation, preserves mandatory grant/activation/rate evidence under projection and never exports token bytes. Shared-profile names are an observed metadata list, not an atomic claim against concurrent profile edits. Public exposure, live provisioning and independent review remain explicit acceptance work.

The typed provisioning action is deliberately skipped by Clap and its descriptor builder is not called by public startup registration. Dispatch can compose that candidate for review, preserving the original request ID and complete envelope. Main captures whether structured argument input consumed stdin before moving the input selector, so secret input cannot silently reuse that stream. The candidate schema requires explicit profiles and exactly one secret source. Development example checks support string-list flags and remove optional fields only while the remaining input still validates, including alternative-required fields.

Dispatch carries an output policy from the registered effect class. Normal read results retain the byte-budget fallback. State-changing handlers preflight complete envelopes before committing; if a handler violates that invariant, final encoding preserves its outcome/recovery data and original failure category, adding an explicit budget warning. An oversized success receives the output-budget exit category while retaining the confirmed result. This last-resort evidence rule is not permission to skip write preflight or emit unbounded provider payloads in normal operation.

Cache loading validates secret bounds and lifetime arithmetic without deserializing persisted product proofs. A fresh cached token gets a new current-user probe for the requested product before a session is returned. Stale tokens are reacquired once from the stored service credentials and verified for every configured target against the original actor before activation. Same-grant contenders reread the committed generation after obtaining the lock, avoiding redundant acquisition. Failed exchange/verification never replaces the previous generation or returns a usable session. A failed local activation returns its uncertain state; confirmed activation receipts survive subsequent session-construction failures. Cleanup-pending receipts remain visible.

Within a process, wall and monotonic expiry both apply. After a restart, the stored wall expiry is checked and the remaining duration receives a fresh monotonic anchor; persisted monotonic timestamps are never interpreted in another process. A wall clock earlier than issuance forces reacquisition. Detecting every cross-restart wall-clock manipulation requires an external trusted clock and is not claimed. Client-credentials acquisition does not rotate the provisioning secret, so a lost token response does not require the delegated-refresh exchange-intent algorithm. These internal methods remain behind the auth CLI/eligibility/independent-review gates.

### Locked credential generations

The native generation adapter opens from validated profile state and the explicit native backend. Its only production credential source is the native vault. Each issued grant uses a private fixed-name lock file under the selected state root, with an exclusive OS lock retained by an unforgeable session guard. Acquisition polls cancellation/deadline without deleting a busy or stale-looking file; the OS releases the lock when the holder exits. File names contain installation/grant identities only. The supported ownership boundary is one principal, one machine and one state root per installation. Cloning a live installation to another root/machine does not gain shared refresh ownership; migration and multi-machine authority remain separate qualification.

A grant has one bounded keyring index containing format, installation/grant binding, storage revision, logical epoch, active manifest, optional staging intent and at most two retired manifests. Manifests name random generations, exact length, 2,048-byte chunk count and SHA-256 digest. The staging intent commits before chunks; complete chunks are read back and verified before the index activates them. Readers reject pending, missing, mixed or corrupt generations. Recovery can activate a complete staged generation; for incomplete staging, the caller-recorded policy either retains the previous complete credential or clears it for reauthorization. OAuth must separately persist exchange intent before an external rotation; this byte store cannot recover a response lost before staging begins.

Activation/logout advance a monotonic epoch. Private version tokens bind installation, grant, epoch and active generation; stale tokens cannot overwrite a later replacement or logout. Cleanup does not change the logical epoch. Logout commits an inactive tombstone before deleting chunks and never deletes the index itself. Cleanup failures after confirmed activation/logout return confirmed receipts with cleanup pending, rather than hiding a committed change. Retired manifests remain indexed until idempotent deletion completes. Failed write acknowledgments are reconciled by exact keyring read-back, with unresolved outcomes preserved. All secret/index bytes stay in keyring items, never SQLite, lock files, logs or artifacts. Auth CLI enablement and independent review remain separate.

Bitbucket and Trello get separate strategies. Bitbucket's OAuth endpoints/scopes/token types and Trello's PKCE/public/confidential callback behavior need provider-specific spikes. The known Trello token-endpoint documentation inconsistency must be resolved before exchange; never try alternate credential endpoints automatically.
