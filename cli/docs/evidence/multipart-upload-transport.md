# Multipart upload transport foundation

This checkpoint implements internal single-file Jira attachment multipart transport. No upload provider/CLI command is registered, and the installed 78-command development bundle is unchanged. [Download evidence](jira-attachment-download.md), [local recovery](local-artifact-recovery.md) and [artifact storage](artifact-store.md) retain earlier binary I/O acceptance. The aggregate binary-transfer and Jira attachment tasks remain incomplete.

`crates/craft-runtime/src/artifacts/streams.rs` opens and verifies a named snapshot against its exact expected SHA-256, retains the same file handle, and performs bounded size/digest verification again while streaming. It exposes no reopenable caller path or raw file handle. Consumed sources cannot enter multipart preparation. EOF verifies exact size/digest and rejects truncation or extension; invocation control is checked around reads. Synchronous native file checks cannot preempt an individual kernel filesystem call.

`transport/multipart.rs` seals one file to the compiled Jira attachment POST route, field file, fixed X-Atlassian-Token:no-check and bounded filename/media metadata. UTF-8 filenames preserve text and escape quotes; controls and path separators are refused. A 70-character boundary derived from canonical metadata and the snapshot digest makes equivalent unsent preparations stable, under the recorded SHA-256 preimage/collision assumptions. The native journal manifest binds framing metadata, source identity, declared length and digest without a local path. File frames are at most 64 KiB, with exact total HTTP length; the suffix is emitted only after the second integrity pass.

`PreparedHttpMutation` reuses its existing single durable claim and persistence paths. Ordinary JSON preparation refuses the multipart command. send_guarded rechecks a borrowed host guard before claim, after claim and throughout HTTP I/O. Cancellation/refusal after claim retains uncertainty and never retries. Success with incomplete source framing becomes an unqualified outcome while retaining its bounded NativeResponse separately in incomplete_upload_response. A sealed VerifiedServiceAccess constructor still requires scope and principal evidence; it does not supply local policy, live settings/permissions or provider response interpretation.

The latter deliberately substitutes a write-sharing test handle to model platforms allowing another writer; production Windows handles additionally deny that writer. This is a controlled native-file fixture, not proof of other-platform qualification or an actual early-response server exchange.

No real credentials, vault writes, live tenant changes, upload activation or new bundle occurred. Other-platform file semantics and a real server response before body completion remain unqualified. The pure response-qualification regression covers that incomplete-framing interpretation without claiming end-to-end early-response acceptance.
