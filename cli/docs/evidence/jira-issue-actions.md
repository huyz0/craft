## Contract and implementation

The [action contract](../jira-issue-actions.md), active provider scenarios and design record define exact expected issue state/assignee, issue-specific account proof, explicit null unassignment and refuse/delete-all subtask semantics before implementation.

`crates/craft-provider-jira/src/issue_context/mutation/actions.rs` brackets narrow issue observations, qualifies only the exact active issue-assignable account and freezes a native action without sending it. Its `actions/input.rs` and `actions/registration.rs` own strict typed inputs, bounded schemas, separately scoped read declarations and fixed PUT-assignee/DELETE routes. `FrozenIssueMutation` retains private optional inert action evidence alongside its existing exact operation/principal/original dual-clock binding. Serialized data cannot recreate it. Action response interpretation recognizes only operation-specific documented acknowledgments/refusals.

`crates/craft-cli/src/issue_mutation/{host.rs,tests.rs}` and `issue_mutation.rs` extend the existing sealed access, complete output preflight, durable claim, final policy/freshness/access checks and completion stack. Trusted host permissions distinguish assignment, unassignment, deletion without children and deletion of all subtasks. None inherits edit/transition authority. The host retains native confirmation independently of persistence/cache effects, and an existing/absent issue or later matching assignment never authorizes replay. Cascade confirms the addressed issue operation without inventing a child enumeration receipt.

Persisted mutation-policy format one still has only edit/transition operations, and typed candidate dispatch still exposes only those two internally. This slice does not widen those records or the public parser/catalog. SQLite schema eight, all existing policy encodings, manifests, lock, dependency inventory and public schema are unchanged.
