# Issue mutation candidates and policy

Public adapters connect `jira issue update` and `jira transition apply` to [the journaled host](jira-issue-mutation-host.md). [Action adapters](issue-action-command.md) extend the same path with assignment, explicit unassignment and deletion. See [current usage](jira-issue-writes.md) and [activation review/evidence](evidence/jira-issue-action-activation.md). Live acceptance remains separate.

Each request supplies a numeric issue, explicit expected issue state, typed changes, operation ID and apply. Transition also supplies an actual transition ID and expected destination status. Expected-state and changes objects can be supplied as bounded JSON flag values or through the ordinary structured-input channel. The input schema requires those objects; parser placeholders cannot become valid input or be sent. Unknown fields, null/missing required objects, malformed/duplicate JSON and local field/apply/output errors fail before opening state or credentials.

Use normal explicit/repository/default profile selection. An optional Cloud ID must match that profile's tenant; otherwise use normal site hints/defaults and the profile tenant fallback. The expected project's numeric ID selects policy, not permission. The issue is always explicit and fresh native issue state must match the expected project/type/status/update before a write can be compiled. Repository hints and ordinary profile defaults provide no write authority.

SQLite schema eight adds `issue_mutation_policies`, keyed by profile and project ID. Each record binds installation, revision, profile, grant, exact Jira Cloud project and expected service actor, plus an enabled flag and an explicit canonical nonempty allowance list. Legacy format one accepts edit and transition only. Trusted updates now write format two, supporting those operations plus independent assign, unassign, delete and delete-all-subtasks allowances. Format-one payloads containing any new action name remain invalid; reads never rewrite or upgrade them. There is no authority inheritance from create, issue-read, project-read or field-read policy. At most 256 project records per profile are accepted through administration.

The trusted setter requires explicit apply, output preflight and expected-revision CAS. Absent revision creates only; a supplied revision updates only that row. Operations are sorted and duplicates/unknown values refused. An enabled record cannot transfer actor or target; disable its existing identity first. Different project rows do not share revisions. Every read validates SQL keys, payload revision and installation/profile/grant/target binding. These records express local host intent, not remote permissions, human review or distributed fencing. Public [policy administration](policy-setup.md) supplies these explicit updates.

Migration from schema seven creates an empty table in the existing state transaction. Prior schemas traverse their existing migrations first. Preserve all existing profiles/settings/grants/policies/journal/cursors. A conflicting table or trigger fails without automatic repair; a failed migration must roll back its version and schema changes. Settings retain format one. Expanded mutation allowances use payload format two through explicit trusted updates, without a further SQLite migration; other policy encodings remain unchanged.

Older binaries refuse schema eight; no downgrade is attempted.

Candidate preparation captures the exact policy row and builds the host's typed project policy. Each host policy checkpoint rereads and compares that full record and selected operation. Missing, disabled or excluded authority denies; other captured changes conflict. Credential-cache and mutation receipts must survive either refusal. Public execution uses native credentials and declared hosts only; synthetic tests exercise the same candidate/host functions with fixed loopback-only credentials.
