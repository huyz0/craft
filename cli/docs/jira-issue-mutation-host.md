# Internal Jira edit and transition host

This host composes [frozen provider preparation](jira-issue-mutation-preparation.md), sealed service access, native HTTP send claims and complete receipts. [Typed adapters and explicit administration](issue-mutation-command.md) supply captured per-project policy. Public activation is now locally qualified after independent review; [usage/evidence](jira-issue-writes.md) retains the live-test limit. Trusted policy explicitly identifies a numeric Jira project, grant, actor and permitted edit/transition operations. Agent input, repository context, read configuration and permission flags cannot supply that policy.

Prepare strict typed input, numeric issue identity, expected state, explicit apply/operation ID, selected output and receipt capacity before state/auth effects. The expected project must equal the trusted project, and both issue and project must identify the same tenant. Fresh issue observations subsequently prove that expected project/type/status/update state. Reject cursors and generic server-CAS preconditions.

Inspect the same operation ID before opening service access and again before metadata work. An existing foreign binding, additional step or started/terminal step refuses further execution. Retain the prior record in the failure response so earlier effects are not represented as a new not-sent attempt. Only a compatible unstarted record can proceed. The normal recovery envelope is budgeted before auth; exceptional already-existing records can exceed that estimate and use evidence-preserving output without starting a write.

Require verified site/grant/actor and all read/write scopes before resource reads. Use the declared metadata read, including expanded transition fields, then compile the private frozen request. Recheck dynamic trusted policy at every native read and before HTTP request construction. Claim the exact native call once through the journal. After claim acquisition recheck access, policy, invocation control and the original metadata freshness before polling HTTP. A failed final preflight leaves a conservative uncertain claim without reopening it.

Run the final dynamic policy check after frozen-context clock verification. A policy change observed during that verification must stop the send rather than follow an earlier successful policy check. This ordering is a local preflight boundary, not an atomic remote permission lock.

Both operations normally return 204. That response confirms processing of the exact bound operation; it does not establish that the issue still has the requested values or destination status after concurrent automation. A contradictory synthetic body is a protocol error while retaining the 204 effect evidence. Edit's documented refusals are 400/401/403/404/409/422; transition's are 400/401/404/409/413/422. An unqualified response, transport failure, timeout or disconnect is uncertain. HTTP 200 is not qualified when the frozen edit requests `returnIssue=false`. A 409 does not prove a Jira CAS mechanism. Provider free-text bodies and URLs never supply diagnostics, authority or retry destinations.

Completion records only provider-qualified outcomes and preserves observed evidence even when receipt recording fails or cancellation has fired. Report operation receipt, target, step, persistence disposition/revision, bounded HTTP request/rate metadata, reconciliation need and independent credential-cache updates. All recovery fields remain selected. `replay_authorized` is always false. Before-send failures retain any prior record; mismatched completion binding cannot turn a foreign attempt into success. Output uses evidence-preserving encoding after an attempt.

There is no automatic reconciliation read or retry. A later matching status/field observation can describe a postcondition, not attribute it to the uncertain request. Unknown outcomes require explicit inspection and a separately qualified recovery decision. This host does not grant deployment, human approval or distributed worker fencing.
