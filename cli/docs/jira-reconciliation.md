# Journal-bound Jira reconciliation

Reconciliation inspects evidence without obtaining a send claim, replaying a mutation or upgrading an unknown outcome from matching current state. The public `operation reconcile` host supports issue create, edit, transition, assignment, unassignment and deletion under separate persisted recovery authority. See [current usage](jira-issue-writes.md) and [activation evidence](evidence/jira-issue-action-activation.md). Live qualification, automatic correlation discovery and async job strategies remain unfinished.

A successful envelope means the investigation completed, not that the original write succeeded. Its assessment can remain unresolved. See [observed qualification and remaining work](evidence/jira-reconciliation.md).

## Binding and authority

Require the operation ID and exactly one source: the explicit original canonical write request, or `--saved` to load the immutable source retained by standalone public issue writes and new reviewed-controller issue-create steps. Saved loading validates the strict source document and recomputed binding; it grants no recovery authority. Legacy and unsupported controller operations without a retained source still require the explicit original. See [saved-source evidence](evidence/saved-request-source.md). Reprepare that request using its existing host descriptor and pure native input validation, then recompute its logical binding under a trusted exact project/grant/actor policy. The journal entry must match the entire binding, including the descriptor digest. Changed payload/target/actor/grant/descriptor fails before auth or resource reads. Never begin or repair a missing journal entry. Missing local evidence cannot establish whether a remote effect exists.

Recovery has its own trusted enabled permission and closed allowed-command list. Existing create/mutation/read policies grant no recovery authority. Native reads use only the issue-read scope, plus the existing service identity-probe scopes. A revoked write scope does not prevent authorized read-only investigation. Original project authority is checked locally and each visible issue must still be in that exact project before its metadata is released.

Schema nine introduces an empty `issue_recovery_policies` table keyed by profile and numeric project. Format-one records bind installation, profile, grant, exact project, expected actor, enabled state, revision and a canonical unique set of original commands: create, update, transition, assign, unassign or delete. Delete here only authorizes read-only investigation of the original issue, regardless of its original subtask mode. No write allowance is inherited or granted. Each profile may have at most 256 project records; existing rows can still be disabled at the limit.

Trusted administration requires explicit apply, complete receipt preflight and exact expected revision. Disable an enabled record before transferring actor or target. Capture and compare the entire record through execution; disabled or excluded operations fail policy checks, and an otherwise allowed changed record fails with a version conflict. Malformed/foreign payloads, unknown operations, duplicate/noncanonical sets, conflicting schema or triggers fail without repair. Migration must preserve existing state and roll back completely on conflict.

The typed candidate requires exactly one non-null explicit original or `saved:true`, an operation ID and optional create-only candidate IDs. Saved requests are resolved before native preparation; explicit null and mixed sources are rejected. Validate original semantics, candidate bounds, fields and budget before state access. Profile/site resolution must agree with the original target, which is never rewritten. Read the separate project recovery record and pass its captured comparison through every host check. Defer native credential construction and locking until journal binding and output preflight establish read targets; local unresolved paths must remain independent of vault availability. These are intended integration semantics, with qualification recorded separately.

## Read strategies

For existing-issue writes, inspect only the original numeric issue ID. For create, combine IDs already confirmed by the relevant journal step with an explicit bounded list of candidate numeric issue IDs. Candidate IDs are investigation targets, not proof that this request created them. At most twenty unique IDs are inspected in one invocation, with no truncation or guessed continuation. Additional unrelated journal steps remain visible as evidence but do not authorize reads of their targets. Empty identity sets return an explicit unresolved assessment without loading credentials or contacting Jira. No arbitrary JQL, guessed marker search, returned URL or cross-site discovery is performed.

Read `project,issuetype,status,updated,assignee` with history updates disabled. Numeric IDs must match exactly. Return only bounded issue identity/state and explicit assignee account identity, never user email, display name, summary/body or returned links. Missing/malformed selected fields fail; explicit null assignee means unassigned. A 404 is absent-or-invisible. Other HTTP failures, malformed bodies, cancellation and deadlines are sanitized and do not retry. Earlier qualified observations survive a later read failure, marked incomplete, unless final authority checks require suppressing them. Observations have individual times and never claim an atomic snapshot.

The assessment is derived from the initial stored submission evidence: no locally started step, recorded confirmation, recorded refusal or unresolved. It is not an overall workflow or job result. A false reconciliation indicator describes stored uncertainty flags only and does not resolve unrecorded secondary effects. An accepted/running/unknown job remains separately represented in the complete journal. A visible candidate, matching assignment/status or later 404 cannot change unknown to confirmed/failed, add a confirmed resource, resolve job completion or authorize replay. Historical confirmation can remain in the receipt even if its issue is now absent or invisible.

## Completion and concurrency

Retain the complete initial journal record, independent credential-cache receipt and qualified native observations. Reread the journal before releasing output. If its binding or revision/content changed, retain the initial and latest validated evidence separately, suppress observations and report a conflict; do not overwrite a competing update or discard newly learned effect evidence. A failed final journal read reports uncertainty rather than assuming the record stayed unchanged. Dynamic policy/access checks run before auth, at every native boundary and after timestamp/output work. Revocation suppresses native observations while preserving journal and credential effects.

Preflight the complete initial-record/recovery output budget before auth. Bound all input and native responses. If later concurrent growth exceeds the selected byte budget, preserve complete recovery evidence under the existing exceptional-output policy rather than hiding known effects. Reconciliation never writes the operation journal, resets a marker, invokes a write endpoint or loads raw credentials in a provider. Its output explicitly says that attribution was not upgraded, the journal was not updated and replay is unauthorized.

## Qualification

Use owned TLS fixtures and actual native journal records for changed/missing bindings, unknown creates, visible/duplicate candidates, absent-or-invisible issues, partial read failure, wrong project, read-only scopes, renewal, late policy/access refusal, cancellation, journal concurrency and no mutation/replay. A double that creates an issue and drops the response must lead to an unresolved assessment or retained known evidence, never a duplicate POST. These checks do not establish provider-side exactly-once behavior, complete candidate discovery, live tenant support or cross-machine fencing.
